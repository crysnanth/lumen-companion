# Relatório técnico — Fase 5: Codex

**Data:** 23/10/2026 (America/Sao_Paulo)  
**Objetivo:** receber eventos reais do Codex CLI e convertê-los em notificações do Lúmen via D-Bus.

## Ambiente verificado

- GNOME Shell 48.7, sessão Wayland.
- GJS 1.82.3.
- Codex CLI instalado: 0.164.0.
- Não havia `~/.codex/hooks.json` nem configuração de hooks no projeto antes desta fase.

## Arquivos criados ou alterados no projeto

- `integrations/codex/hook-mapper.js`: converte quatro nomes de hooks no contrato de eventos Lúmen, omitindo prompts e dados de ferramentas.
- `integrations/codex/hook-adapter.js`: lê uma linha JSON da entrada padrão e chama o método D-Bus local com limite de tempo e tamanho; falhas são silenciosas para não interferir na execução do Codex.
- `integrations/codex/hooks.json`: associa `UserPromptSubmit`, `PermissionRequest`, `Interrupt` e `Stop` ao adaptador.
- `tests/codex-hook-mapper.test.js`: cobre mapeamentos, descarte de dados privados e ausência de inferência de sucesso a partir de `Stop`.
- `docs/codex-integration.md`: registra instalação, eventos, privacidade e limitações.
- `docs/reports/2026-10-23-fase-5-codex.md`: este relatório.

## Arquivos do usuário

- Instalado `~/.codex/hooks.json` com modo `0600`. O arquivo não existia antes; nenhum backup foi necessário.
- O `config.toml` existente não foi editado manualmente. Ao confiar os hooks na interface `/hooks` do CLI, o próprio Codex acrescentou quatro hashes sob `[hooks.state]`, como metadados de confiança. As configurações de projeto, interface, plugins e `node_repl` permaneceram no arquivo.
- A confiança fica associada ao hash de cada definição. Alterar um comando requer nova revisão no Codex.
- A extensão Lúmen foi habilitada para o teste e depois desabilitada, restaurando o estado anterior. O arquivo instalado da extensão corresponde ao código do projeto.

## Eventos e mapeamentos

| Hook Codex | Evento Lúmen |
|---|---|
| `UserPromptSubmit` | `task_started` |
| `PermissionRequest` | `approval_required` |
| `Interrupt` | `task_interrupted` |
| `Stop` | `idle` |

`Stop` não confirma sucesso. O adaptador não devolve decisões para conceder ou negar permissões. Campos como prompt, entrada de ferramenta, texto final e comandos são descartados; somente hook, sessão e turno são usados para formar o evento.

## Comandos e verificações

```bash
python3 -m json.tool integrations/codex/hooks.json
gjs -m tests/codex-hook-mapper.test.js
gjs -m tests/state-machine.test.js
printf '{"hook_event_name":"UserPromptSubmit","session_id":"test-session","turn_id":"test-turn","prompt":"conteúdo privado de teste"}\n' | gjs -m integrations/codex/hook-adapter.js
install -m 600 integrations/codex/hooks.json "$HOME/.codex/hooks.json"
codex
# na interface do CLI: /hooks, revisar e confiar as quatro definições
```

Resultados observados:

- O JSON dos hooks foi validado.
- Os testes do mapeador e da máquina de estados passaram.
- Com o serviço indisponível, o adaptador terminou com código 0 e sem saída em `stdout` ou `stderr`.
- Em um GNOME Shell 48 aninhado e recém-iniciado, o serviço D-Bus ficou disponível. Uma chamada de teste direta respondeu `(true, 'working', '')`.
- No teste inicial isolado, uma instrução segura do Codex CLI em modo somente leitura disparou `UserPromptSubmit`; o monitor D-Bus registrou a chamada `NotifyEvent` com `kind: task_started`, identificadores de sessão/turno e texto genérico. O processo de teste foi interrompido antes de observar `Stop`; depois, a sessão principal foi testada até o fim do turno.
- Após logout/login e habilitação da extensão pelo usuário, a sessão GNOME principal anunciou o serviço D-Bus. Uma segunda tarefa segura do Codex CLI concluiu com código 0; o monitor observou `task_started` seguido de `idle`, e o CLI registrou ambos os hooks como concluídos.
- A extensão permanece habilitada (`ACTIVE`) na sessão principal.

## Problemas encontrados

A sessão GNOME principal iniciou às 09:15, antes de os módulos da ponte D-Bus serem instalados às 09:49. Nessa sessão, a extensão mostrava estado `ACTIVE`, mas o nome D-Bus do Lúmen não aparecia. A causa provável é que a sessão antiga manteve em memória a versão previamente carregada dos módulos. O registro no Shell aninhado recém-iniciado confirmou que o código atual anuncia o serviço e recebe a chamada.

O usuário fez logout/login e habilitou a extensão. A ponte foi validada na sessão principal, sem reinício forçado do GNOME Shell.

## Limitações

- O escopo da integração é somente o Codex CLI. Outras interfaces do Codex ficam fora do planejamento atual.
- Os hooks utilizados não comunicam um resultado estruturado de falha nem uma pergunta `input_required`.
- O hook `PermissionRequest` apenas apresenta aviso. A aprovação continua na interface original do Codex.

## Restauração

Para remover a integração do perfil Codex, remova `~/.codex/hooks.json` e desabilite Lúmen em Extensões do GNOME. O metadado `[hooks.state]` pode permanecer no `config.toml`; sem uma definição correspondente, ele não executa hooks.

## Resultado e pendências

A Fase 5 cumpriu o critério de observar eventos reais do Codex CLI chegando à ponte D-Bus na sessão principal. A avaliação da necessidade de um daemon Rust está registrada separadamente.
